# Design system

MatchRadar is dark by default, with an optional light theme. Both use the same layout and semantic CSS variables in `src/styles.css`: panel RGB, text, muted text, accent, accent surfaces, card surfaces, and borders. Dark uses charcoal glass and lime; light uses pale green-white surfaces, ink text, and a deeper green accent. Avoid per-component color inversions or duplicated theme layouts.

Panel opacity ranges from 70% to 100%, defaulting to 96%. Apply it to the panel background, never the shell's CSS `opacity`, so text, controls, and crests stay opaque. Home, settings, and details share the same panel treatment. Cards retain stronger surfaces for legibility; verify contrast over bright and dark wallpapers at the lowest opacity.

Keep rounded corners, compact typography, tabular scores, and consistent badge/team/result alignment. The header contains branding and native minimize/hide controls; the footer contains Settings, pin, following filter, and refresh. Toggle buttons expose pressed state and match their Settings switches. Compact mode reduces the native window and layout together; it is not minimization.

Use one content scroll surface, fixed header/footer, visible keyboard focus, and reduced-motion support. Inspect home, Teams, Appearance, and details at 390px and the 320px minimum width, including the compact window. Check packaged Windows at 100%, 125%, and 150% scaling separately from browser layout checks.

Static widget surfaces suppress the browser context menu and accidental text selection. Keep native editing menus and selection in inputs, textareas, selects and editable content. Mark intentionally copyable text with `data-copyable` (currently operation errors); its selection and context menu remain available. Do not intercept pointer-down, focus, keyboard or clipboard events to enforce this policy.

The competition marks are original inline illustrations, not official league assets: the crown/football shield for the Premier League and a star ball for the Champions League, plus a paired mark for Both. They use the theme accent and have no remote-image dependency. Club crests come from validated ESPN CDN URLs with a canonical stable-ID fallback, then initials if images fail. These provider-owned assets do not imply distribution rights; see `DATA_PROVIDER.md`.

The competition bar (the summary row under the hero) contains the selector: an emblem, competition name, context line and chevron in a compact button that opens a three-option listbox. It must stay one tab stop with Arrow-key option movement, Escape to close and focus return. In Both mode each card shows a tiny `PL` or `UCL` tag in the result metadata with the full competition as its accessible name; do not add a second header or per-card colour scheme. At 320px the context line hides and the name truncates so the live pill remains visible.

Match cards have sibling details and notification buttons, never nested interactive buttons. Bell state is exposed with `aria-pressed`, a match-specific accessible name, and an explanatory tooltip. A ringing bell enables the match subscription; a struck bell means explicitly muted; an outline bell uses team defaults. Footer filtering uses a list-filter icon, a state tooltip, and an active dot. Date headings use semantic headings with clearer weight and a divider; the list states its approximate 14-day coverage. The expanded default remains 390×700 after inspection at 320px/390px; larger secondary labels and slightly roomier card actions improve legibility without a larger window.

Match details keep the score central but move live status out of the score line: a status pill sits beside the competition (`LIVE 45'+3'`, `HALF-TIME`, `FULL-TIME`, `SCHEDULED`), and cards use a small clock pill above the score. Overview is the default tab and puts goals/scorers first, followed by key stats, latest events and venue. Timeline uses half headings, team badges and compact event labels (GOAL, YELLOW, SUB, ON TARGET), never truncating words to a fixed character count. Lineups use two team tabs with formation and shirt numbers; starters are labelled as the kickoff XI and substitutions show their provider minute. Match alerts live behind a bell control in the details header and open a small popover, so Overview, Timeline and Lineups never reserve layout space for alert controls.

## Spacing, reading and interaction refinements

Teams settings uses three groups in this order: **Followed clubs** (favorites first, unfollow in place), **Premier League clubs** (static catalog plus any club seen in a PL fixture, excluding followed clubs), and a collapsed **Other clubs** disclosure for discovered non-PL sides. Search spans all three groups and reveals other clubs while typing. Membership moves between groups without duplicating a club, and focus follows the moved club. Keep the existing 36px club row and checkbox styling; do not add nested scroll regions.

Use the shared `.shell` spacing tokens (4/8/12/16/20px), a 16px page gutter (12px at narrow widths), and a 10px settings-row rhythm (8px in compact view). Keep component rules together instead of appending overrides. The header is 56px (50px compact); the footer is at least 52px (48px compact), with 32px toolbar targets and separate status/timestamp lines. Settings use a 64px subheader and compact tab strip. Let short sections end naturally; never stretch controls or resize the native window when switching tabs.

Secondary settings/detail text is 12px; footer and match status text is 11px. Match names can wrap to two lines and retain full-name titles and full accessible button names. Scores remain tabular. Use semantic warning/scrollbar tokens in both themes. Low-opacity light panels use stronger muted ink (`#2E4234`) for readability; background opacity must leave foreground CSS opacity at 1.

The Premier League pill counts confirmed live matches across the entire snapshot, independently of Following only. Saved scores stay visibly saved, and a failed scoreboard with no confirmed live observations says Live unavailable. The filter changes cards only, displays a small list hint, and offers Show all matches when it hides all results. Empty schedules, loading, partial failures and saved data remain distinct. Local day headings reconcile at midnight and on focus/visibility return without requesting provider data.

Keep one quick bell on each card. Its accessible name, tooltip and `data-alert-state` distinguish team defaults, all alerts on, and explicit mute. Match Details contains the individual Use team settings action; removing one override must preserve all others. Ended matches cannot gain new subscriptions from the card; details still allow existing alerts to be muted/reset. Alerts explains followed-team defaults separately from match bells and retains the shared reminder time. No delivery logic belongs in these components.

View navigation focuses the new heading, then restores the originating card/Settings control and list scroll on return. Escape returns to matches, while native selects retain their own Escape behavior. Settings implements the [WAI-ARIA tabs pattern](https://www.w3.org/WAI/ARIA/apg/patterns/tabs/) with selected state, tab/panel relationships, one tab stop, Arrow keys and Home/End. Browser-only minimize/hide/startup actions are disabled with explanations. Keep focus rings and reduced motion intact.

When an action removes its own button, keep focus in the active view: resetting a match override or muting an ended match focuses the alert heading, resetting all bells focuses the Alerts panel, and clearing an empty search focuses the search input. An open match retains its most recent score if a subsequent snapshot omits it, marking an unconfirmed live score as saved. Existing detail content stays visible without an additional skeleton during a refresh.

Compact mode remains a persisted native display preference, off by default. Rust already requests a 460px logical starting height and retains expanded dimensions; users can still manually resize. Browser compact preview changes CSS spacing only. Do not infer actual window sizing, restart/DPI behavior or Windows text scaling from browser screenshots; use the acceptance checks in `VALIDATION.md`.
