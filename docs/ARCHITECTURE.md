# Architecture

## Responsibility map

| Boundary | Owner |
| --- | --- |
| Native commands, state locks, task wakes, polling/delivery loops and tray lifecycle | `src-tauri/src/main.rs` |
| Provider backoff deadlines and bounded sleep chunks | `src-tauri/src/scheduling.rs` |
| Logical window sizing, resize calls and best-effort settings rollback | `src-tauri/src/window.rs` |
| Serialized state, defaults, preference normalization and feed application | `src-tauri/src/model.rs` |
| ESPN transport/normalization and source-result reconciliation | `src-tauri/src/provider.rs`, `src-tauri/src/refresh.rs` |
| Atomic state storage and recovery | `src-tauri/src/persistence.rs` |
| Notification eligibility and durable submission queue | `src-tauri/src/alerts.rs`, `src-tauri/src/delivery.rs` |
| Delivery and summary regression tests (private child modules) | `src-tauri/src/delivery_tests.rs`, `src-tauri/src/details_tests.rs` |
| Native event subscriptions, view navigation and focus restoration | `src/App.tsx` |
| Optimistic preference queue and ordered snapshot reads | `src/store.ts` |
| Shared IPC types, presentation helpers and local-date timer | `src/types.ts`, `src/presentation.ts`, `src/useLocalDay.ts` |
| Cards, details, settings and shared controls; semantic theme/spacing rules | `src/components/`, `src/styles.css` |

`get_snapshot` returns the Rust snapshot serialized in camelCase; TypeScript models its UI-facing subset, not internal persisted notification/window fields. Rust `Option` values can serialize as null. `save_settings` accepts a complete Settings object assembled by the frontend's partial-update queue and returns normalized authoritative Settings. Snapshot events signal a new read rather than transporting an additional state model. Keep these names, nullability and defaults aligned when changing the IPC contract. The window-helper and delivery-test extractions do not change it.

The Tauri process owns a normalized snapshot, preferences, a local JSON cache and a single asynchronous refresh loop. React reads snapshots through commands and refreshes on native events. The window can be hidden while the process continues running. The ESPN adapter validates each fixture independently, and failed requests preserve the previous snapshot. Settings and notification identifiers are persisted together.

The frontend shell and native event listeners stay in `src/App.tsx`. Focused presentation components in `src/components/` own settings tabs, match cards/alert shortcuts, details, crests and shared controls. They call the existing store with partial settings patches; the Rust preference/notification model is unchanged. League status derives from the complete snapshot, separately from filtered card groups. `src/useLocalDay.ts` supplies one local-midnight timer plus focus/visibility reconciliation for date headings, independent of networking. Successful snapshot reads clear obsolete load/refresh errors while retaining unrelated save/action failures and provider diagnostics.

Snapshot persistence lives in `src-tauri/src/persistence.rs`, preserving the existing JSON schema. Writes use exclusive same-directory temporary files, `write_all`/`sync_all`, close the handle, then replace by `std::fs::rename` (Windows replacement support; no delete-before-rename). Before replacing `state.json`, the previous primary must deserialize successfully and is atomically published as `state.json.bak`. A first save seeds the backup with the validated new snapshot. Backup failure aborts the primary save. If a primary is missing but a valid backup exists, an ordinary save preserves that backup. Existing snapshot-lock serialization prevents concurrent in-process writers.

Startup distinguishes missing, unreadable, and invalid files. Defaults are allowed only when both primary and backup are genuinely absent. An invalid primary is copied into an exclusive, synced `state.json.corrupt-<pid>-<counter>` diagnostic file before a valid backup is atomically restored; damaged data is never rotated into the backup. Invalid backups are also preserved before replacement. Read/archival/recovery failures return path-specific errors without overwriting damaged originals or substituting defaults; startup deliberately stops if recovery is unsafe. Successful recovery is logged to `provider.log` without dumping user state. Orphaned `.tmp-*` files from a killed process are ignored, not promoted; ordinary failed writes clean up their own temporary file.

F01 tests cover legacy/full snapshot round trips, corruption, unreadable state, invalid backups, recovery failures, injected partial writes/disk-full, sync and replacement failures, and abandoned temps. Windows execution is still required: local Rust tests are blocked by missing MSVC `link.exe`. Check real NTFS replacement, sharing/antivirus locks, permissions/disk exhaustion, and process termination at save boundaries. File sync plus same-directory replacement is not a guarantee against every hardware/power-loss or nonstandard filesystem failure; backup recovery remains essential. No installer was built for this change.

The poller targets 60 seconds for live fixtures, five minutes when a fixture is within a day and 30 minutes otherwise. Fixture snapshots use monthly queries refreshed every six hours; daily score updates are merged by stable match ID. Manual refresh forces both. Failure delays grow exponentially; numeric Retry-After is honored up to one hour. Failures leave the previous snapshot intact and write diagnostic details to `provider.log`. The implementation has not yet been tested against actual sleep/resume or rate-limit responses.

Settings saves are separate from data refresh. Appearance, pinning, favorites/filtering, and notification preferences persist and emit a snapshot event without waking the poller or changing feed timestamps. A demo/live mode transition wakes refresh while preserving the real feed; a generation counter prevents older requests from repopulating a different mode. The frontend queues partial preference edits, overlays pending edits on snapshots, and rolls back failed saves without discarding later unrelated edits. Rust remains authoritative after persistence.

The root window participates in the taskbar (`skipTaskbar: false`); the permitted frontend minimize command is separate from hide-to-tray. Rust applies pin changes and compact sizing. Compact mode targets a logical height of 460px and width no greater than 390px, respecting narrower windows; expanded dimensions are stored in the snapshot and restored when compact is disabled. The window-state plugin restores first, then compact sizing is applied explicitly to avoid competing startup restores. Native operation/persistence errors are returned to the UI.

Settings deserialize with dark-theme defaults and opacity clamped to 70–100. `teamCatalogVersion` migrates old favorite IDs once, independently of provider match identities. `expandedSize` stores logical dimensions so display scaling is not baked into the saved expanded size. Native window restoration and actual taskbar behavior still require packaged Windows verification.

`src-tauri/src/alerts.rs` plans notifications independently of native delivery so eligibility, timing, and persistence can be tested deterministically. Settings hold `matchAlerts` keyed by stable match ID: missing uses followed-team switches, enabled opts into reminder/start/goal alerts regardless of those switches, and disabled mutes that match even when a club is followed. Resetting match bells restores team defaults. The reminder lead time is shared. A bell opt-in explicitly enables goal alerts for that match; team goals remain off by default.

Match overrides, observation baselines, score high-water totals, pending events, and submitted event IDs persist in the local snapshot. Enabling/resetting an override re-primes its observation while retaining the score ceiling; the next successful observation establishes a baseline instead of reporting historical starts or goals. Stale observations and score corrections are suppressed conservatively; a legitimate goal coinciding with the first observation or a rebound to a previously observed total may be skipped. Team and match eligibility feed one event planner, so overlapping subscriptions cannot generate two candidates for the same event. Only a successful notification API submission records a sent ID; this is not a display/read receipt.

Expiry is derived by Rust from the known kickoff, not trusted from the client. Completed/cancelled overrides are removed after a day from kickoff; absent or unresolved fixtures retain overrides until 30 days after the last known kickoff. A changed kickoff extends expiry. Cleanup runs at startup and successful polling, preserving overrides across short outages. Saving a bell preference does not cause network refreshes. Compact remains off for new installations, and saved compact/expanded preferences are preserved.

## Durable notification submission (F04)

`src-tauri/src/delivery.rs` separates confirmed transition detection, persisted pending candidates, and submission acknowledgment. Existing deterministic IDs (`match:reminder`, `match:start`, `match:score:home:away`) and legacy sent IDs/baselines are unchanged. `pendingNotifications` and `notificationRetryAfter` have backward-compatible defaults. Persisted entries validate identity, payload size, timestamps, lifetime, and attempt count; invalid records are skipped individually, duplicate IDs are removed, and the queue is capped at 64. Overflow is logged and omitted, never recorded as submitted.

The poller queues events only from F03's confirmed observations; saved/unconfirmed active scores cannot advance baselines or create events. A previously confirmed pending event can still retry during a provider outage except after demo, when fresh confirmation is required. A separate native task sleeps until a queue deadline or notification-specific wake; it never calls ESPN or wakes its poller. Settings saves cancel newly muted/ineligible work without a network request. Demo mode pauses submission and preserves eligible real candidates. New daily-confirmed score corrections can cancel an obsolete pending goal; unconfirmed monthly scores cannot.

Candidates, baselines, attempt counts, and next-attempt times are saved through the F01 repository before each native call. Exposed temporary failures retain the same event with 30/60/120/240-second retry delays, at most five total attempts, subject to expiry. Goals expire five minutes after detection, starts after ten, and reminders at kickoff (at most 120 minutes after detection). Exhausted candidates suppress repeats until expiry; none are falsely marked sent. Cancelled/postponed fixtures and reminders rescheduled outside the lead window are removed. An exposed permission-denied/missing/unsupported notification service error persists a shared 30-minute submission pause, preventing a failure storm across matches. Diagnostics go to stderr and the existing `provider.log`, without notification bodies or user-facing error toasts.

Acknowledgments are persisted after a successful API return. If that save fails, the running process retains the sent ID and retries persistence without resubmitting. Persistence errors pause submission with 60/120/240/300-second capped backoff; poll/settings wakes cannot bypass this pause. A crash after native acceptance but before the acknowledgment reaches disk can still cause a duplicate after restart. This is bounded best-effort submission, not exactly-once OS delivery.

Important boundary: the locked `tauri-plugin-notification` **2.8.0** Windows implementation prepares a notification, dispatches `notify-rust::Notification::show()` on a background task, and discards that task's result. Its desktop `permission_state()` also always returns Granted. MatchRadar can retry preparation/submission errors exposed by the plugin, but cannot observe later OS failures or infer real Windows permission status from it. Successful plugin dispatch does not prove OS acceptance, display, or user attention; Focus Assist/system-disabled notifications can remain invisible. No dependency or native API replacement is included in F04. See the [official notification plugin guide](https://v2.tauri.app/plugin/notification/); this finer acknowledgment limitation was verified against the locked crate's `src/desktop.rs`.

F04 adds 15 deterministic sink/clock/persistence tests for fail-once, repeated failures and retry limits, pending restarts, expiry (including stalled writes), repeated observations, subscription overlap/muting, corrections, first observations, service unavailability, F03 stale data, queue validation/capacity, legacy state, and F01 repository round trips. These Rust tests remain **unexecuted locally** because MSVC `link.exe` is missing. Consolidated Windows CI must compile/run them; packaged Windows tests must separately cover native failures, restart/crash boundaries, real notification settings, hidden-tray operation, and sleep/resume. No installer was built for F04.

## Match Centre evolution checkpoint

`details.rs` normalizes eng.1 summaries into events, statistics and players. `get_match_details` accepts only numeric IDs already in the widget fixture cache and rejects demo requests. A separate async cache lock serializes summary requests independently of scoreboard operations. The bounded 24-entry cache is saved in `Snapshot.detailCache` through F01; old state defaults to an empty cache and malformed individual entries are skipped. Summary fields never change scores or notification observations. Active details refresh at 60 seconds only while mounted; other entries reuse a 15-minute cache. Failures retain cached data and impose a minimum 60-second cooldown. `useMatchSummary` ignores responses after cleanup/navigation; `MatchCentre` renders supported sections inside the existing Details scroll region. Home view filters use existing fixture data only.

## Integration hardening checkpoint

`details.rs` now separates HTTP parsing from cache application with injectable clock/transport results. Freshness accepts nonnegative ages only; cooldown reads do not extend deadlines. Restoration validates and bounds entries; F01 recovery coverage includes detail cache, settings and pending/sent notification records. The frontend retains same-match data while retrying and pauses detail-specific polling while hidden, with identity/demo/navigation guards. Match Centre sections use the accessible tabs pattern and precede match-alert controls in the same Details scroller.

`scheduling.rs` owns the poller's monotonic backoff gate. Manual refreshes coalesce while a fetch is active and cannot bypass provider backoff. Explicit Retry-After is not capped to one hour; only sleep chunks are bounded to prevent timer overflow. Mode changes can enter demo without network work while retaining the real-provider deadline. Normal successful adaptive intervals and source freshness/notification logic remain unchanged. See MATCH_CENTRE_EVOLUTION_REPORT.md for verification and remaining Windows checks.

## Rich demo and recent results

Demo mode provides fictional events, statistics and lineups for live and completed examples. The frontend derives the manually stepped Manchester derby from a session-local stage; no simulated score or summary enters the native feed or notification planner. Demo fixture timestamps are anchored when entering demo. Synthetic summaries never invoke summary HTTP or enter the real details cache. Optional CDN crests and offline fallback badges are unchanged. Real feed and alert data stay persisted separately from projected demo fixtures and demo match preferences. Pending delivery is paused in demo and requires fresh scoreboard confirmation after returning; expiry is still enforced. See [Demo Mode report](DEMO_MODE_REPORT.md).

Demo fixture, scenario, summary and associated frontend tests live under `src/demo/`; the native fixture generator lives in `src-tauri/src/demo.rs`. These modules do not yet create a build-time exclusion boundary. Shared Match Centre rendering uses paired statistic and grouped lineup components. See [Demo isolation report](DEMO_ISOLATION_REPORT.md) before considering a public build.

Real Results uses `results.rs` and `get_recent_results`, separately from the live feed. Opening Results requests the current/previous calendar months as needed to cover the previous 14 UTC dates through today; monthly queries are verified ESPN behavior. Completed fixtures only are retained, capped at 200. Successful history is cached for six hours in the F01 snapshot; repeated filter switches use that native cache. Failed/partial batches retain successful/cached results, keep the prior success time, and set an independent retry deadline (at least five minutes). No history request runs merely from mounting Home. Regular completed scoreboard observations are merged by ID without changing the upcoming window. Historical IDs are eligible for on-demand summaries only after opening their cards. Results have their own loading, source timestamp, empty/error and Retry states.

Historical data has no path into `delivery::enqueue` or live alert baselines. Existing source errors/timestamps, settings and notification state survive history writes. Mode-generation checks prevent an old real response being committed during a demo/live transition. No dependencies or permissions changed.
